# Planner and archive implementation notes

Baseline main: 829aa1928e19ce683ab30061f2c38adaa893df91. Dashboard polish follows the supplied Visual Product Polish playbook and previously reviewed OpenDesign/Portfolio Motion Stories guidance: stable targets, readable glass backing, restrained warm accents, useful grouped controls, natural layout and rendered verification. No new animation/editor engine or artwork is installed.

The public website design is preserved. New event-stories-public.js is a content adapter loaded by the existing script.js only on event routes. Before approved data exists it leaves the authored cards, flyers, recordings and page structure in place. Approved data can update original poster placements, enrich the existing event modal, and update the existing dedicated recording page; it does not replace the frontend layout/styles or create calendar bookings.

Fifty source entries were imported as unapproved records. Existing files/links remain available; missing factual fields are intentionally not inferred. Event galleries and recording fields are functional authoring data, with a local new-tab preview. Native MP4/WebM clips below 3 MB use the authenticated unique media-upload path; longer recordings use hosted URLs. Vercel asset deployment can lag upload; local draft previews use independent in-memory blobs so a later local-file change/deletion cannot invalidate preview playback.

Home uses two independent aligned stacks and dated planning/calendar items. Selected dates prefill the event form. With Airtable unavailable, saving creates a shared event-story planning draft, not a calendar write. When connected, staff calendar actions retain the existing table/Publish semantics. Story creation can create an unpublished Airtable record and store its returned id; the systems are not an atomic cross-service transaction. Inspect/reload after ambiguous create failures before retrying. There is no durable deployment worker, recurring-event scheduler, booking engine or per-user role system implied by this release.

Airtable staff reads are private/no-store and include all pages. Public feed pagination and Los Angeles date comparisons are consistent. Known stale PATCH/DELETE versions and conflicting Public field overrides are rejected. These checks reduce stale writes but do not make Airtable read/check/write atomic. Public debug access requires staff login. Live Airtable acceptance remains dependent on real credentials, writable fields and override configuration; fixture verification must not be described as a real production write test.

Event-story publication sends only approved records to public JSON and retains other working records as an unserved shared draft. The client uses the returned publishedContent/draftSha and preserves local data on partial/conflicting saves. Shared drafts are excluded from website output, but this public repository is not a confidential store. All original Weddings venue sections remain; individual wedding stories are an additional library bridge with explicit publication permission.
